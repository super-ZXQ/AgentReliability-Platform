# 平台化大阶段 · 从评测门禁到质量闭环

## 最终目标

在现有 V1 上完成一套可连续演示的流程。对固定源码执行质量扫描，复现一个失败，关联诊断证据，在 Docker 沙箱验证候选补丁，再运行原故障复测和回归，输出可供人工审核的报告。通过同一报告体系呈现语义评分、模型与 Harness 对照、安全扫描。阶段内按下文顺序连续实现和验收。

截至本轮交接，M4 已实现真实模式，pytest 32 项通过，离线报告 20/20 通过。真实模型报告的 18 条记录为 `NOT_RUN`，缺少本地模型配置。M3 远端红绿检查是历史证据，报告应标明对应提交。

## 执行约定

- 保留现有 `run`、`compare` 和 20 条离线回归。先查 Git 状态、运行 pytest，保留已有改动。上游仓库用固定提交的独立 checkout，跨项目依赖用独立进程或官方 API。
- 每个子任务完成后运行对应测试，记录命令、退出码、版本和报告路径，直接进入下一项。模型凭据、Docker 服务或远端授权缺失时，把该项的具体实跑标为 `NOT_RUN` 并继续独立工作。优先完成适配代码、契约测试和可复制的复测命令。
- 联网模型实验沿用显式开启的方式，并仅使用合成数据或已授权公开样本。测试替身、离线回放、真实服务分别标注。远端发布、审批和生产操作由用户授权，本阶段交付可审阅的本地候选产物。

## 1. 封存 V1 证据

复跑 pytest 与现有 20 条离线门禁，保留 M3 的红绿报告和链接。具备 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` 时，执行 V1 真实模式的 6 条用例各 3 次，使用新产物目录。报告给出 18 次任务的判定、错误和时延。应用侧已拦截的请求记录模型调用为零。

```sh
uv run --locked agentreliability run --mode live --allow-network --repeat 3 --target-dir .targets/commerce --out artifacts/v1-release/live
```

## 2. 统一证据并接入 VibeCheck-AI

新增一个本地入口，目标命令为 `agentreliability quality --scenario orders-slow-query --out artifacts/platform/orders-slow-query`。用轻量运行清单记录 `run_id`、目标仓库和 SHA、场景、变体或补丁摘要、子任务状态、执行方式和产物。子任务保留自己的外部运行 ID、源文件或步骤及原始证据引用，HTML 只展示脱敏字段。用固定版本的上游适配器，锁定工具提交。

- 首个闭环场景用 IncidentPilot 的 `reference/orders_api` 和 `fault_002_slow_database_query`。从同一份固定源码取静态扫描输入与动态场景的基线。电商套件继续作为独立的 Agent 回归，报告注明各自的目标和提交。
- VibeCheck-AI 初始锁定 `3a0e22c7e49eb317cbecb80c4d7616668938300e`。从独立进程调用真实 `app.scanner.sensitive.scan_directory`，转出规则 ID、等级、相对路径、行号与脱敏片段。单独用合成命中样例验证规则与脱敏，再扫描闭环场景的源码。报告标明本次扫描范围。[VibeCheck-AI](https://github.com/super-ZXQ/vibecheck-ai)
- 测试同一报告可追溯到真实扫描，且错配 SHA、缺失产物、上游退出失败和超时各有明确状态。重跑使用新的运行目录。

## 3. 接入 IncidentPilot 并跑通沙箱复测

IncidentPilot 初始锁定 `566639ea876eed171c705ad0c1a0d79276b8584b`。参考上游审计流程，从隔离的临时数据库和工作区运行单一场景，读取真实运行 ID、工具调用、证据、诊断和补丁产物。用平台适配器调用上游流程，保留原 checkout。先跑离线调查，标明脚本化模型和工具。若有已授权配置，另做一次真实 MCP 或模型调查，并独立标注执行方式。[IncidentPilot 上游审计](https://github.com/super-ZXQ/incidentpilot/blob/566639ea876eed171c705ad0c1a0d79276b8584b/docs/audit/INCIDENTPILOT_EVALUATION.md)

闭环验收顺序如下。

1. 固定场景的原版本先被故障断言判为失败。将失败事件连到调查和支持根因的证据。预期根因只交给验证器。
2. 在隔离 Docker 工作区应用候选补丁。记录基线 SHA、补丁摘要和测试结果。运行仍带故障条件的独立断言，再运行健康路径回归。两项通过才生成待人工审核产物。
3. HTML 展示扫描、失败、诊断证据、补丁、复测和审核状态。明确该场景是注入的模拟延迟。Docker 不可用时保留实际诊断和适配测试，沙箱实测标为 `NOT_RUN`。

## 4. 增加语义评分、交叉实验和安全扫描

| 子任务 | 实现与验收 |
| --- | --- |
| OpenJudge | 接一个语义评分器，评判诊断摘要是否有证据支持。建立含支持、不支持和边界例子的版本化样本，冻结校准与留出划分，记录标签来源。具备人审标签及模型配置后，在留出集报告一致率、误判和分歧例。离线测试验证适配器和计分逻辑。评分独立展示，离线硬门禁沿用确定性断言。[OpenJudge](https://github.com/agentscope-ai/OpenJudge) |

## 5. 交付与停止条件

- 仓库给出从依赖准备到一条质量闭环的复现命令。报告按目标和执行方式分组，并能追到真实扫描、失败证据、补丁及复测。用 M3 的 REL-01 保留一条简短的测试开发演示。
- pytest 与完整 20 条离线套件通过。验证缺失或不匹配的证据、沙箱失败和服务超时都不会生成通过状态。CI 保留失败报告。
- 最终给出每个子任务的实现状态、实跑状态、命令与产物路径。只有所有可执行项完成并验证后才收尾。将确需用户提供的凭据、人工标签、Docker 服务或远端授权汇总为一次补验清单，列出各自精确的继续命令。
